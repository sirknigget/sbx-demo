# Dotfiles demo guidance

## Purpose and scope

This directory is a small example of a Docker kits v3 sandbox built from `shell-docker`. The host builds one kit for either a local sandbox with a mounted workspace or a cloud sandbox with a GitHub clone; both link tracked home files. Local setup can optionally move private agent state from an older sandbox. Keep the example small: OMP, Pi, Codex, Claude Code, Node.js, Bun, Bash, Git, example subagents and skills, and two cleanup commands. Do not add MCP, unrelated tooling, or personal paths. Keep all work for this demo inside `dotfiles/`. The user's `agent-sbx2` sandbox is outside this demo and must not be accessed or changed.

Read `README.md` in this directory for host setup and command examples. Keep it short and user facing: build and launch steps for local and cloud, plus compact explanations of mounts, clones, links, and credentials. Do not put agent guidance there. The parent repository has its own guidance; do not change its files for dotfiles work.

## Ownership and data boundaries

- `Dockerfile` owns the ARM64 image, pinned OMP/Node.js/Bun installs, and first-boot copies of `home/`. Build it with `dotfiles/` as the Docker context. Do not put credentials or runtime state in the image.
- `sbx-demo.yaml` owns the v3 workload definition and optional OpenAI/Anthropic credential capabilities. Its privileged capability is optional so the same kit can run where that capability is unavailable. Either provider, both providers, or neither may be stored before creation. Local and cloud use separate `sbx` secret stores; real credentials stay with Docker's managed proxy, while runtime configuration contains placeholders only. `configure-provider-auth` writes only private credentials and runtime overlays, never repo-linked user settings, and seeds the provider CLIs and OMP's runtime overlay; `omp-managed` and `pi-managed` select an available provider while preserving each tool's own login flow when neither is present. Pi uses its native ChatGPT provider with an unsigned JWT-shaped OAuth placeholder in its private auth file; Docker injects the real token through its proxy.
- `home/` owns tracked, secret-free Bash and Git settings, OMP configuration, example agents and skills, and `.local/bin/` commands. It is copied into the image for first boot. `home/.local/bin/link-tracked-home` later links individual tracked files from the mounted checkout or cloud clone into `/home/agent`; it must not replace OMP's runtime database or installed OMP binary. Track `.codex/config.toml`, `.codex/sandboxd.config.toml`, `.claude/settings.json`, and `.pi/agent/settings.json` as individual files, never the credential or state directories. Minimal defaults bootstrap agents before their first launch. Edits to linked files become active without rebuilding the image; cloud changes must reach its clone through Git. The sandbox `codex` and `claude` launchers wrap the installed npm binaries with their permission bypass flags; `omp-managed` explicitly uses YOLO approval mode and `pi-managed` trusts project files with `--approve`. OMP and Pi user defaults apply when invoked directly too.
- `copy-state.sh` owns optional local-to-local agent state export and import through `staging/`; cloud setup does not use it. It moves OMP’s database and `.env`, `~/.codex/`, `~/.claude/`, `~/.claude.json`, and `~/.pi/agent/`. `agent-state-copy.py` skips caches, binaries, and symlinks, protects destination symlinks, and snapshots SQLite databases. `omp-db-copy.py` uses SQLite backup so WAL-backed databases remain consistent. Stop all four agents before exporting or importing. Keep `staging/` ignored by Git and excluded from Docker builds. Review and remove copied private data when the transfer is complete.
- `regenerate_sandbox` is the host composition root. Both modes use the dedicated `sbx-demo-kit` Docker builder, refuse to replace an existing `sbx-demo`, and preserve the host's selected builder. Local mode takes an absolute `--workspace-mount` containing this checkout, optionally exports from `--old-name`, creates the sandbox with VirtioFS cache and Docker shared skills disabled, and saves a clean timestamped template under `~/agent-sandbox-backup/` before importing private state. It links repo home files and skills, checks tools and provider status, and runs OMP, Codex, and Pi OpenAI inference checks only when configured; no paid Anthropic request is made. Cloud mode takes `--cloud` without a mount or state migration, builds for Linux ARM64, clones the HTTPS GitHub origin to `/home/agent/workspace/sbx-demo`, links home files there, and checks installed tool versions. Cloud and local sandbox names live in separate stores.
- `dev-demo` is a host launcher for OMP, Pi, Bash, Codex, or Claude Code in `sbx-demo`. Local mode reads the explicit `SBX_DEMO_WORKSPACE` mount path and keeps the caller's directory relative to that mount; the shared `workspace/` layout is a recommendation, not a fixed path. With `--cloud`, it maps the caller's path within this checkout to the cloud clone and dispatches `sbx --cloud exec`. Cloud mode does not use `SBX_DEMO_WORKSPACE`.

## Example commands and maintenance

The OMP settings are in `home/.omp/agent/config.yml`. The example agents are `reader`, `command-runner`, and `env-setup`; the example skills are `planning`, `grilling`, `agent-workflow-issue-report`, and `sbx-dotfiles-sync`. Keep these examples self-contained and free of references to tools not installed by this demo.

Codex and Claude each have a tracked `demo-reader` subagent and a `SessionStart` hook. Both hooks use `home/.config/sbx-demo/session-start.sh`; keep it quick and free of credentials or transcript logging. Codex rejects symlinked agent files, so link its secret-free `agents/` directory; other settings and Claude agent files are individually linked. The image itself creates Claude’s skills alias to `.agents/skills` before the clean template is saved.

`clear_caches` handles npm and npx caches, not Bun. `clear_docker` removes containers and images; build cache and volumes need separate interactive consent. Both offer `--dry-run`, prompt before a default cleanup, and accept `--confirm` for noninteractive cleanup without optional Docker pruning. Keep their responsibilities separate.

Host setup scripts and `dev-demo` must work with Bash or Zsh; the sandbox uses Bash only. Run image builds, sandbox creation, and `dev-demo` only on the host. Do not run host scripts or build the image from inside a sandbox. Cloud cannot mount host paths, so keep its clone path and local path mapping aligned. In a sandbox, use focused syntax checks and isolated home/state smoke checks when changing the corresponding files. Verify the changed path without running host-side commands or using real OMP credentials. Run isolated regression checks with `python3 -m unittest discover -s dotfiles/tests -v`. These use temporary homes and mocked host commands; they never create real sandboxes.
